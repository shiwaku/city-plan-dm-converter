# dm-converter

## 概要

DM（数値地形図データファイル）をGeoJSON形式に変換します。線・面・記号・方向・注記の5種類に分割して出力します。

出力したGeoJSONは、QGIS等での地図表示のほか、tippecanoe・pmtiles によるベクトルタイル化を経て Web地図の背景地図として利用できます。

## 都市計画基本図とは

都市計画基本図とは、都市計画法（昭和43年法律第100号）第6条に定める「都市計画に関する基礎調査」および第14条に定める「都市計画図書」の**背景図**（白図）として使用される地形図です。

**公共測量成果**として品質を確保するため、公共測量作業規程の準則により、航空測量による新規取得・現地調査・数値図化などの作成手順と対象地物が定められています。都市計画部局が主体となって整備・更新することがほとんどで、更新頻度は5年間隔程度の場合が多いとされています。

統合型GISの普及に伴い、都市全体を網羅する都市計画基本図は地方公共団体内の共用空間データとして整備されており、都市計画部局にとどまらずハザードマップ作成など他部署での活用も増えています。また国土地理院に提出され、基盤地図情報としてとりまとめられ公開されます。

正式な規格名は**数値地図**（DMデータ）ですが、自治体によって呼称が異なります。いずれも実態は同一のデータです。

| 自治体での呼称例 | 実態 |
|---|---|
| 都市計画基本図 | 同一データ |
| 地形図 | 同一データ |
| 白図 | 同一データ |

> 出典: 国土交通省「[都市計画情報のデジタル化・オープン化ガイダンス 第1.0版 p.10](https://www.mlit.go.jp/toshi/tosiko/content/001618641.pdf#page=11)」（令和5年6月）

### 縮尺と地図情報レベル

地図情報レベルとは、国土地理院が定める数値地図の精度区分で、縮尺と対応しています。都市計画基本図では主に以下が使われます。

| 縮尺 | 地図情報レベル | 主な用途 |
|---|---|---|
| 1/25,000 | 25,000 | 都市計画基礎調査・都市計画図書の背景図 |
| 1/20,000 | 20,000 | 都市計画基礎調査・都市計画図書の背景図 |
| 1/10,000 | 10,000 | 都市計画基礎調査・都市計画図書の背景図 |
| 1/2,500 | 2,500 | 都市計画基礎調査・都市計画図書の背景図 |

> 都市計画図書のうち、総括図は25,000分の1以上、計画図は2,500分の1以上の縮尺が要件です（都市計画法第14条）。

## 対応範囲

現状では、DMデータのうち**都市計画基本図**（地形図・白図）に対応しています。

対応するレコードタイプは以下のとおりです。

| RecordType | 名称 | 対応 |
|---|---|---|
| E1 | 面 | ○ |
| E2 | 線 | ○ |
| E3 | 円 | − |
| E4 | 円弧 | − |
| E5 | 記号（点） | ○ |
| E6 | 方向 | ○ |
| E7 | 注記 | ○ |
| E8 | 属性 | − |

### DMデータの構造

DMファイルは固定長のレコードが並んだテキストファイル（文字コードは Shift-JIS）です。本ツールが地物として読み取るのは次の2種類です。

| レコード | 役割 |
|---|---|
| 図郭レコード（`M`で始まる） | 図郭番号、図郭南西端の平面直角座標、収録要素数などの図郭単位のヘッダ |
| 要素レコード（`E`で始まる） | 個々の地物。先頭2文字がレコードタイプ（`E1`〜`E8`） |

このほかに `H`（グループヘッダ）・`G`（グリッドヘッダ）・`T`（TIN）のレコードが現れることがありますが、本ツールでは地物として扱わず読み飛ばします。

各要素の座標は、**図郭南西端の座標（メートル）＋ センチメートル単位の相対値**として格納されています。本ツールはこれを合成して平面直角座標を復元し、EPSG:4326 へ変換します。この構造は縮尺に依存しないため、変換処理も縮尺を問いません。

線（E2）・面（E1）は座標列を6点ずつ後続レコードに格納します。始点と終点が一致する線は面として扱われるため、入力が E2 でも出力は面（`RecordType` が `E1`）になる場合があります。

## 利用方法

DMファイルを `input/<縮尺>/` フォルダに配置してから実行します。

```bash
# 縮尺1/2500、座標系はデフォルト（EPSG:6676）
node src/index.js

# 縮尺1/10000
node src/index.js --scale 10000

# 縮尺1/25000（自治体によっては1/25000で整備されている）
node src/index.js --scale 25000

# 入力座標系を指定する場合
node src/index.js --epsg 6675

# 入力フォルダを直接指定する場合
node src/index.js --scale 2500 --input /path/to/dm_folder
```

よく使う2つは npm scripts でも実行できます。

```bash
npm start            # node src/index.js と同じ（1/2500）
npm run start:10000  # node src/index.js --scale 10000 と同じ
```

### 静岡市データでの実行例

[静岡市オープンデータ](https://data.bodik.jp/dataset/221007_1712212695)の都市計画基本図（1/2,500・1/10,000）で、[デモのビューワ](https://shiwaku.github.io/dm-converter/)のデータを作った際の手順です。

**1. DMファイルを配置する**

ダウンロードした `.dm` ファイルを縮尺ごとのフォルダに置きます。`.dmi`（索引ファイル）が同梱されていても読み飛ばされるため、そのまま置いて構いません。

```
input/
├── 2500/     # 123ファイル・628MB
└── 10000/    # 10ファイル・251MB（+ index10000.dmi）
```

**2. 一括ビルドを実行する**

静岡県は平面直角座標系第VIII系なので、`--epsg` / `EPSG` の指定は不要です（既定値が 6676）。

```bash
npm run build            # 1/2,500 と 1/10,000 を一括（scripts/build.sh 2500 10000）
```

DM→GeoJSON→GeoParquet→MBTiles→PMTiles まで通ります。各段の詳細は[一括ビルド](#一括ビルドgeojson--geoparquet--pmtiles)を参照してください。GeoJSON だけ欲しい場合は `node src/index.js --scale 2500` のように変換だけを実行します。

**3. 生成物**

| | フィーチャ数 | PMTiles | ズーム範囲 |
|---|---:|---:|---|
| 1/2,500 | 2,274,166 | 84MB | ZL15〜16 |
| 1/10,000 | 984,449 | 39MB | ZL2〜14 |

このほかに縮尺ごとに GeoJSON 5ファイル・GeoParquet 5ファイル・MBTiles が `output/` に出ます。

**部分的な焼き直し**

GeoJSON を作り直さずに後段だけやり直す場合は環境変数で段を飛ばします。

```bash
# タイルだけ焼き直す（tippecanoe のオプションを変えたとき）
SKIP_CONVERT=1 SKIP_PARQUET=1 npm run build

# GeoParquet だけ焼き直す（GeoJSON より古くなっているとき）
SKIP_CONVERT=1 SKIP_TILES=1 npm run build
```

**タイルサイズの確認**

生成した PMTiles のタイルサイズ分布は [vt-optimizer-rs](https://github.com/unvt/vt-optimizer-rs) で確認できます。

```bash
vt-optimizer inspect output/kihonzu_10000.pmtiles
```

### オプション

| オプション | デフォルト | 説明 |
|---|---|---|
| `--scale` | `2500` | 縮尺（入力フォルダ名と出力ファイル名に使用） |
| `--epsg` | `6676` | 入力データの座標参照系（EPSGコード） |
| `--input` | `input/<scale>/` | DMファイルが格納されたフォルダ |
| `--jobs` | CPUコア数 − 1 | 並列変換のワーカー数。`1` で逐次実行 |

### 処理時間

`.dm` ファイル単位でワーカーに分けて並列処理します。ファイルを連続したかたまりで分割し、断片を元の順序で連結するため、**出力は逐次実行とバイト単位で同一**です。`--jobs 1` で逐次実行に切り替えられます。

静岡市データでの実測値（16コア、出力先は WSL から見た `/mnt/c`）は次のとおりです。

| 入力 | フィーチャ数 | 逐次（バッファリング前） | 逐次 | 並列 |
|---|---:|---:|---:|---:|
| 1/10,000（10ファイル・251MB） | 98万 | 7分28秒 | 41秒 | **12秒** |
| 1/2,500（123ファイル・628MB） | 227万 | 約15分（推定） | 1分42秒 | **29秒** |

**メモリと一時領域はワーカー数に比例して増えます。** 1ファイル分の要素をメモリに展開してから書き出す作りのため、上記の実測では 1/2,500（15ワーカー）で最大3.7GB、1/10,000（12ワーカー）で1.8GBを使いました（逐次は1.0GB）。メモリの少ない環境では `--jobs` で絞ってください。また変換中は、最終出力とほぼ同じサイズの断片ファイルが一時ディレクトリ（`os.tmpdir()`）に作られます（1/2,500 で約1GB）。処理の最後に削除されます。

大きく効いたのは並列化よりも書き込みのバッファリングです。従来は1フィーチャごとに `fs.writeSync` を2〜3回呼んでおり、1/10,000 でも約295万回の syscall が発生していました。`/mnt/c` のような低速なファイルシステムではこれが処理時間の8割を占めます（実時間7分28秒に対しCPU時間は1分3秒）。まとめ書きにしてCPU律速になってから、並列化がさらに3倍強を稼いでいます。

`--scale` は入出力パスのラベルにのみ使われ、パース処理や座標変換には影響しません。DMデータの座標は図郭南西端座標＋センチメートル単位の相対値という実座標で格納されているため、正の整数であれば任意の縮尺（1/500、1/5000、1/25000 など）を指定できます。

### 出力ファイル

`output/` フォルダに以下の5ファイルが生成されます。

| ファイル名 | 内容 |
|---|---|
| `都市計画基本図_<縮尺>_線.geojson` | 線要素（E2） |
| `都市計画基本図_<縮尺>_面.geojson` | 面要素（E1） |
| `都市計画基本図_<縮尺>_記号.geojson` | 記号・点要素（E5） |
| `都市計画基本図_<縮尺>_注記.geojson` | 注記要素（E7） |
| `都市計画基本図_<縮尺>_方向.geojson` | 方向要素（E6） |

出力されたGeoJSONはQGIS等に読み込むことで地図表示や、tippecanoe等のツールを使ってベクトルタイルへの変換が可能です。

なお、[対応範囲](#対応範囲)に記載のとおり、E3（円）・E4（円弧）・E8（属性）は未対応のためスキップされます。

### 出力GeoJSONの属性

5ファイルすべてに共通する属性：

| 属性名 | 説明 | 例 |
|---|---|---|
| `Code` | 分類コード（DMの層番号） | `1106` |
| `Elno` | 要素識別番号（`図郭番号-分類コード-要素番号`） | `08ND392-1106-0001` |
| `RecordType` | レコードタイプ | `E1`（面）、`E2`（線）、`E5`（記号）、`E6`（方向）、`E7`（注記） |
| `DataType` | データタイプ（日本語） | `面`、`線`、`点`、`方向`、`注記` |
| `DataKind` | 実データ区分 | `0`（データなし）、`2`（二次元）、`4`（注記） |

注記（E7）のみに追加される属性：

| 属性名 | 説明 | 例 |
|---|---|---|
| `Text` | 注記文字列 | `300` |
| `Vnflag` | 縦横フラグ | `0`（横書き）、`1`（縦書き） |
| `Angle` | 文字の角度（度） | `86` |

方向（E6）のみに追加される属性：

| 属性名 | 説明 | 例 |
|---|---|---|
| `Angle` | 向きの角度（度） | `-155` |

#### 方向（E6）について

方向要素は、起点と方向点の2点で1件を構成します。第1点が地物の位置、第1点から第2点へのベクトルが向きを表します。

2点間の距離は図上の記号長に相当する定型値（1.00m / 1.25m / 5.00m 前後で全体の大半）であり実長ではないため、**線としては出力せず、起点のみを点として出力し、向きは `Angle` 属性に変換**しています。

`Angle` は水平右（東）を0度とする反時計回りの度数で、注記（E7）の `Angle` と同じ規約です。描画側は同じ変換で扱えます。

分類コードによって描かれ方が2通りあります。流水方向（5241）は矢印記号ですが、坑口（4219）・鳥居（4207）・灯ろう（4205）などは記号自体を `Angle` の方向へ回転させて描くものです。

#### `Code`（標準図式コード）について

`Code` は公共測量標準図式で定められた地物種別の識別コード（4桁数字）で、DMでは層番号として格納されています。道路・建物・植生・地形などの地物がこのコードで区別されます。

ベクトルタイル化してWeb地図で表示する際は、このコードをキーにスタイルを振り分けます。特に記号（E5）では、`Code` とスプライト（アイコン画像）を紐付けることで、公共測量標準図式に従ったシンボル表示ができます。

> 出典: 国土地理院「[作業規程の準則](https://www.gsi.go.jp/gijyutukanri/gijyutukanri41018.html)」中「[付録7 公共測量標準図式](https://www.gsi.go.jp/common/000258741.pdf)」

#### 注記の描画について

注記（E7）は代表点のポイントとして出力され、文字列は `Text`、描画向きは `Vnflag`（縦書き／横書き）と `Angle`（角度）で表現されます。測量ベンダーからGeoJSONで受領する場合は「注記_横」「注記_縦」のように縦横で別ファイルに分かれていることがありますが、本ツールは1ファイルにまとめ、`Vnflag` で区別します。スタイル設定時は `Vnflag` でフィルタしてください。

## QGIS での表示

記号（E5）・方向（E6）・注記（E7）は代表点のポイントとして出力するため、GeoJSON や GeoParquet をそのまま QGIS に読み込むと、いずれも同じ点マーカーが並ぶだけになります。地物の種別・向き・文字は属性として持っているので、スタイルを当てて初めて図として読めるようになります。線・面も、既定ではランダムな色で描かれます。

出力5種すべてのレイヤスタイルを [`qgis/`](qgis/) に同梱しています。

| ファイル | 対象 | 内容 |
|---|---|---|
| `都市計画基本図_線.qml` | 線（E2） | 歩道（2213）は破線、等高線（7101〜7104）は細線、建物（3001〜3004）はやや太い実線で描き分け |
| `都市計画基本図_面.qml` | 面（E1） | 塗りなし＋黒の輪郭（線図と重ねる前提） |
| `都市計画基本図_記号.qml` | 記号（E5） | `Code`（分類コード）ごとに地図記号を表示。凡例には公共測量標準図式の名称を併記 |
| `都市計画基本図_方向.qml` | 方向（E6） | `Code` ごとの地図記号を `Angle` に従って回転 |
| `都市計画基本図_注記.qml` | 注記（E7） | `Text` をラベル表示し、`Angle` で回転、`Vnflag` で縦書きに切替。1/2,500 以上に拡大したときのみ表示 |

**データファイルと同じフォルダに、拡張子を `.qml` に替えた名前で置くと自動で適用されます。** 例えば `output/都市計画基本図_2500_記号.qml` を置けば、`都市計画基本図_2500_記号.parquet` でも `.geojson` でも、読み込むだけでスタイルが当たります。手動で当てる場合は、レイヤプロパティの「スタイル」→「スタイルの読み込み」→「ファイルから」で指定します。

```bash
# 例: 出力先に5種類ぶんを縮尺ごとに配置する
for scale in 2500 10000; do
  for kind in 線 面 記号 方向 注記; do
    cp "qgis/都市計画基本図_${kind}.qml" "output/都市計画基本図_${scale}_${kind}.qml"
  done
done
```

### 地図記号について

記号と方向は、ビューワと同じ [dm-sprite](https://github.com/shiwaku/dm-sprite)（MIT License）のアイコンで描きます。SVGは [`qgis/symbols/`](qgis/symbols/) に `dm-<コード>.svg` として置いてあり、`.qml` にはこれを base64 で埋め込んでいます。**QGIS 側でSVGパスを設定する必要はありません**（`.qml` 単体で記号が出ます）。

参照先は本家 [geolonia/smartcity-dm-sprite](https://github.com/geolonia/smartcity-dm-sprite) ではなく fork です。静岡市データで使う記号のうち6コード（2219 / 3519 / 3531 / 5227 / 6335 / 7212）が本家に無かったため、標準図式から作図して追加してあります。作成手順は fork の [アイコン作成ガイド](https://github.com/shiwaku/dm-sprite/blob/main/docs/icon-authoring-guide.md) にまとめています。

**スプライトに収録されていない分類コードは、地図記号ではなく代替のマーカーで描かれます。** 記号は色付きの丸、方向は赤い三角です。凡例には名称が出るので、どの地物かは判別できます。静岡市データで該当するのは以下の1コードだけです（記号は68コード中67、方向は12コード中12が地図記号で描かれます）。

| 対象 | Code | 名称 | 代替 |
|---|---|---|---|
| 記号 | 6110 | 被覆 | 丸 |

6110「被覆」は標準図式では**線記号**（E2、上縁を4号線・他を2号線で描き、上縁に直径0.4mmの半円を2.0mm間隔で付す）として定義されており、点アイコン化は妥当でないため意図的に作成していません。実データでも点2,542件に対し線71,271件・面25,923件と点は少数派です。

どのコードが代替になったかは、生成スクリプトの実行時にも一覧が出ます。なお、ビューワでもこのコードは同じ理由で記号が表示されません。

表示サイズの既定は 9mm です。SVGは 64×64 のキャンバスに対して絵の占有率が中央値で3割ほどしかないため、**指定値に対して見た目は3分の1程度**になります（9mm で実際のインクは3mm前後）。大きさを変えたい場合は `--icon-size` で指定して作り直してください。

```bash
node scripts/make-qgis-styles.js --icon-size 12
```

### 注記の見え方について

DMの注記は密度が高く、広い範囲を表示すると文字が重なって読めません。そのため注記のスタイルでは次の2つを既定にしています。

- **1/2,500 以上に拡大したときだけ表示**（縮尺分母が 2,500 を超えると非表示）
- **重なるラベルは描かない**（QGIS の衝突回避に任せ、重なった分は間引く）

どちらも作り直し時に変更できます。文字サイズの既定は 7pt です。

```bash
node scripts/make-qgis-styles.js --label-min-scale 5000  # 1/5,000 から注記を出す
node scripts/make-qgis-styles.js --label-size 8          # 文字を大きく
```

重なっても全部出したい場合は、生成後にレイヤプロパティの「ラベル」→「レンダリング」で「重なるラベルを表示」を有効にしてください。

### 出典・承認文言を画面に表示する

測量成果の使用承認では、調製品に所定の文言を明記することが条件になっている場合があります（[利用上の注意](#利用上の注意)を参照）。QGIS では「著作権ラベル」の装飾として地図の隅に常時表示できます。

1. メニューの **ビュー → 装飾 → 著作権ラベル**
2. 「著作権ラベルを有効にする」にチェック
3. テキスト欄に文言を貼り付ける
4. **配置**を「右下」にする

キャンバスに表示されるほか、「プロジェクト → インポート/エクスポート → 地図を画像にエクスポート」で書き出した画像や、印刷レイアウトの地図アイテムにも入ります。設定はプロジェクト（`.qgz` / `.qgs`）に保存されるため、レイヤスタイル（`.qml`）とは別に、プロジェクトごとに設定してください。

静岡市の都市計画基本図を使う場合の文言は次のとおりです（承認書で特定されているため変更しないこと）。

```
この地図は静岡市長の承認を得て、同市所管の2,500分の1及び10,000分の1静岡市地形図を使用して調製したものである。（承認番号07静都都第2068号）
```

### 角度の読み替えについて

本ツールの `Angle` は水平右（東）を0度とする反時計回り、**QGIS のマーカー回転は時計回り**です。マーカーの絵がどちらを向いて描かれているかによって、必要な読み替えが変わります。

| マーカー | 角度0での向き | QGIS に与える式 |
|---|---|---|
| 地図記号（SVG） | 右（東） | `0 - to_real("Angle")` |
| 代替の三角マーカー | 上（北） | `90 - to_real("Angle")` |

ラベルの回転は QGIS も反時計回りのため、注記では `Angle` をそのまま使います（縦書きの場合のみ0度に倒します）。

なお、出力される属性はすべて文字列型です（`Angle` も `"86"` のような文字列）。QGIS の式で数値として扱うには、上のように `to_real()` を挟んでください。

### スタイルの作り直し

記号・方向のカテゴリは、実データに出現する分類コードから作っています。同梱しているものは静岡市データの記号68コード・方向12コード分（＋「その他」）です。他自治体のデータで作り直す場合は、変換後に次を実行します。

```bash
node scripts/make-qgis-styles.js                    # output/*_記号.geojson・*_方向.geojson から収集
node scripts/make-qgis-styles.js --codes 3509,4201  # 記号のコードを直接指定
```

スプライトに記号が無いコードや、付録7に名称が無いコードは実行時に一覧が出ます。

分類コードの名称は `viewer/src/dmCodes.ts` の対応表（付録7 公共測量標準図式）を参照しています。

## 一括ビルド（GeoJSON + GeoParquet + PMTiles）

GeoJSON だけ作り直して GeoParquet や PMTiles が古いまま残ると、配信データと変換結果が食い違います。`scripts/build.sh` で最後までまとめて焼き直せます。

```bash
npm run build                    # 1/2,500 と 1/10,000 を一括
bash scripts/build.sh 2500       # 縮尺を指定
bash scripts/build.sh 2500 10000 25000
```

実行される処理は次の3段です。

1. **DM → GeoJSON**（`src/index.js`）
2. **GeoJSON → GeoParquet**（`ogr2ogr -f Parquet`）
3. **GeoJSON → MBTiles → PMTiles**（`tippecanoe` → `pmtiles convert`）

ズーム範囲は縮尺から自動で決まります（[最大ズームレベルの決め方](#最大ズームレベルの決め方)の表と同じ値）。未定義の縮尺を指定した場合はタイル生成のみスキップされ、`zoom_range` への追記を促すメッセージが出ます。

### 環境変数

| 変数 | 効果 |
|---|---|
| `EPSG=6675` | 入力データの座標参照系を指定 |
| `SKIP_CONVERT=1` | DM→GeoJSON を飛ばし、既存のGeoJSONから後段だけ作り直す |
| `SKIP_PARQUET=1` | GeoParquet を作らない |
| `SKIP_TILES=1` | MBTiles / PMTiles を作らない |

### 必要なツール

いずれも無ければ該当する段だけスキップされ、変換自体は完了します。

| ツール | 動作確認バージョン | 用途 |
|---|---|---|
| [OSGeo4W](https://trac.osgeo.org/osgeo4w/) の ogr2ogr | GDAL 3.9.3 | GeoParquet 生成 |
| [tippecanoe](https://github.com/felt/tippecanoe) | v2.80.0 | ベクトルタイル生成 |
| [go-pmtiles](https://github.com/protomaps/go-pmtiles) | v1.30.3 | PMTiles 変換 |

> **GeoParquet には Parquet ドライバを持つ GDAL が必要です。** conda 版・Debian 版の GDAL は既定で Parquet ドライバを含みません。スクリプトは `PATH` 上の `ogr2ogr` を調べ、Parquet 非対応であれば WSL 環境の `C:\OSGeo4W\bin\ogr2ogr.exe`（見つからなければ `C:\OSGeo4W64\bin\ogr2ogr.exe`）へ自動でフォールバックします（Windows形式のパスへの変換も行います）。

## ベクトルタイル作成（参考）

以下は `scripts/build.sh` が内部で実行している内容です。手動で調整したい場合の参考として残しています。

縮尺ごとに別々の PMTiles を作成し、表示側で切り替えるのが基本の構成です（[viewer/](viewer/) はこの方式）。

| 縮尺 | tippecanoe のズーム範囲 | 最大ZL | ビューワでの表示範囲 |
|---|---|---|---|
| 1/25,000 | `-Z2 -z12` | 12 | — |
| 1/10,000 | `-Z2 -z14` | 14 | z2〜z14.99 |
| 1/2,500 | `-Z15 -z16` | 16 | z15〜 |

最小ズームは、その縮尺のタイルを何倍まで引いて表示したいかで決めます。1/10,000 を `-Z2` としているのは、広域に引いた状態でも背景図として表示し続けるためです。一方 1/2,500 は z15 以上でのみ表示するため `-Z15` から作成します。

各縮尺を1ファイルにまとめたい場合は `tile-join` で結合できますが、その際はズーム範囲が重複しないよう割り当て直してください（例: 1/10,000 を `-Z13 -z14` にする）。表示側で切り替える構成では重複して問題ありません。

### 最大ズームレベルの決め方

ベクトルタイルは座標をタイル内の整数格子（0〜4,095）に量子化して格納するため、変換時にわずかな位置誤差が生じます。元データの精度を損なわないよう、**格子間隔（分解能）が地図の許容誤差以下**になる最小のZLを最大ズームレベルに選びます。

- **許容誤差** = 縮尺分母 × 0.1mm（図上0.1mmに相当する地上距離）
- **分解能** = 赤道周長 40,075,016.686m ÷ (2^ZL × 4,096)

| 縮尺 | 許容誤差 | 最大ZL | そのZLの分解能 | 1段下のZLの分解能 |
|---|---|---|---|---|
| 1/25,000 | 2.5m | **12** | 2.389m | 4.777m ✗ |
| 1/20,000 | 2.0m | **13** | 1.194m | 2.389m ✗ |
| 1/10,000 | 1.0m | **14** | 0.597m | 1.194m ✗ |
| 1/5,000 | 0.5m | **15** | 0.299m | 0.597m ✗ |
| 1/2,500 | 0.25m | **16** | 0.149m | 0.299m ✗ |

分解能は赤道基準の最大値で、実際には緯度 φ において cos φ 倍に小さくなります（静岡市付近の北緯35度では ZL16 で約0.12m）。したがって上表のZLであれば日本国内では余裕をもって許容誤差を満たします。

### タイルサイズの基準（1タイル 1,250KB）

ベクトルタイルの設計では、**1タイルあたり 1,250KB** が実務上の基準になります。Mapbox Tiling Service が明示している上限で、超えた分はレイヤーごとに予測不可能な形でフィーチャが削除されます。

> Each tile has a limit of 1250 kilobytes.
>
> — [Mapbox Tiling Service / Vector tiles](https://docs.mapbox.com/mapbox-tiling-service/ja/vector/)

タイルの担当範囲はズームが下がるほど広くなるため、**低ズームほどこの上限に当たりやすい**という非対称性があります。ZL0 は世界全体が1タイルなので、そのズームで描くデータすべてが 1,250KB に収まらなければなりません。都市計画基本図のように市域全体を1つのタイルセットで低ズームまで作ると、ZL9〜11 で1タイルが数MBに達します。

タイルサイズの分布は [vt-optimizer-rs](https://github.com/unvt/vt-optimizer-rs) の `inspect` で確認できます。同ツールの `--max-tile-bytes` の既定値も 1,280,000 バイト（= 1,250KB）で、この基準を超えたタイル数が `Tiles over limit` として出ます。

```bash
vt-optimizer inspect output/kihonzu_10000.pmtiles
```

上限に収めるための手段は、効果の大きい順に次のとおりです。本リポジトリでは前2つを採用しています。

| 手段 | 内容 | 本リポジトリ |
|---|---|---|
| 属性を削る | 描画に使わない属性を `-y` で落とす。特にフィーチャごとにユニークな文字列（IDなど）は文字列辞書を大きく膨らませる | [タイルに残す属性](#タイルに残す属性) |
| 描かないフィーチャを落とす | スタイル側の `minzoom` で描かれないものを `-j` でタイルから除外する | [低ズームで描かれないフィーチャの除外](#低ズームで描かれないフィーチャの除外) |
| ジオメトリを簡略化する | `-S` で低ズームの頂点を減らす。`--simplify-only-low-zooms` を併用すれば最大ズームの精度は保たれる | 未適用 |
| フィーチャを間引く | `--drop-densest-as-needed` などで密集部を落とす | 未適用（`-r1` の方針と衝突する） |
| ズーム範囲を分ける | 低ズームは粗い縮尺のタイルセットに任せる | 縮尺ごとに別タイルセット |

### tippecanoe のオプション

| オプション | 意味 |
|---|---|
| `-Z` / `-z` | 最小／最大ズームレベル |
| `-r1` | ポイントの間引きを無効化。**記号・注記では必須**（付けないと点が間引かれて消える） |
| `--no-feature-limit` | タイルあたりのフィーチャ数上限を解除 |
| `--no-tile-size-limit` | タイルサイズ上限を解除 |
| `-L` | レイヤー名を指定して入力ファイルを追加 |
| `--force` | 既存の出力ファイルを上書き |
| `-j` / `--feature-filter` | ズームや属性でフィーチャを絞り込む（[低ズームで描かれないフィーチャの除外](#低ズームで描かれないフィーチャの除外)を参照） |
| `-y` | タイルに残す属性を指定（[タイルに残す属性](#タイルに残す属性)を参照） |

密集地物でタイルサイズが問題になる場合は `--drop-densest-as-needed` の併用を検討してください。

### タイルに残す属性

`-y` でビューワの描画に必要な属性だけを残しています。GeoJSON 側の属性は削っていないため、QGIS などで全属性を使う用途には影響しません。

```
-y Code -y Text -y Angle
```

| 属性 | 用途 |
|---|---|
| `Code` | 全レイヤーの描き分け（フィルタ・アイコン名） |
| `Text` | 注記の文字列 |
| `Angle` | 記号・注記の回転角 |

落としている属性とその理由:

| 属性 | 理由 |
|---|---|
| `Elno` | 要素識別番号。フィーチャごとにユニークな文字列で、タイル内の文字列辞書を最も膨らませる |
| `RecordType` / `DataType` / `DataKind` | レイヤー内で単一値のため情報量がない |
| `Vnflag` | 縦横フラグ。現状のビューワは未使用（縦書き注記を実装する場合は復活させる） |

1/10,000（ZL2〜14）での実測値:

| 条件 | 総容量 | 最大タイル | 1,250KB超 | 平均タイル |
|---|---|---|---|---|
| フィルタなし | 83.10MB | 5.51MB | 15 | 363.64KB |
| 建物の除外のみ | 74.49MB | 4.54MB | 14 | 325.95KB |
| 建物の除外 + 属性の絞り込み | 44.90MB | 2.54MB | 5 | 196.50KB |
| さらに低ズームの描画外フィーチャを除外（現行） | **38.98MB** | **1.74MB** | **3** | **170.59KB** |

ジオメトリは変わらず、線レイヤの属性キーが5個→1個、値の辞書が422,382個→61個に減ります（ZL13で計測）。**属性の絞り込みのほうが建物の除外より削減効果が大きい**ことに注意してください。

1/2,500（ZL15〜16）は属性の絞り込みのみが効き、116.38MB → 83.62MB、最大タイル 340.68KB → 241.96KB になります。

なおビューワのポップアップは、残した属性しか表示できなくなります。

### 低ズームで描かれないフィーチャの除外

ビューワは低ズームではレイヤーの一部しか描きません（`viewer/src/layers.ts` の `minzoom`）。タイルに入れたままだと、描かれないのに転送とデコードのコストだけがかかります。`-j` の条件をビューワの `minzoom` と対応させて、描かれないフィーチャをタイルから落とします。

| レイヤー | 除外条件 | 対応するビューワの `minzoom` |
|---|---|---|
| 面 | 建物 `3001`〜`3004` を ZL13未満 | 建物は低ズームでは骨格に不要 |
| 線 | 建物を ZL13未満、等高線 `7101`〜`7104` を ZL12未満 | `line_contour`: 12 / `line_building`: 13 |
| 記号 | レイヤーごと ZL13未満 | `symbol`: 13 |
| 方向 | レイヤーごと ZL13未満 | `direction`: 13 |
| 注記 | ZL13未満（基準点等のみ ZL12未満） | `annotation`: 13 / `annotation_kijunten`: 12 |

**`scripts/build.sh` の閾値はビューワの `minzoom` と対になっています。片方を変えたら両方直してください。** 対応表は [viewer/README.md の「1/10,000 レイヤー一覧」](viewer/README.md#110000-レイヤー一覧)にあります。

除外の効果が最も大きいのは建物です。面レイヤはフィーチャの約9割が建物（`3001` 普通建物・`3002` 堅ろう建物・`3003` `3004` 無壁舎）で、これがないとZL9〜11で1タイルが数MBに達します。次に大きいのが等高線で、線レイヤのフィーチャの約17%を占めます。

建物を除外する条件は次の形になります。

```
-j '{"kihonzu_10000_polygon": ["any", [">=", "$zoom", 13], ["!in", "Code", "3001", "3002", "3003", "3004"]],
     "kihonzu_10000_line":    ["any", [">=", "$zoom", 13], ["!in", "Code", "3001", "3002", "3003", "3004"]]}'
```

- `Code` は文字列属性なので、除外値も文字列で指定します。
- `$zoom` は整数のタイルズームに対する判定です。MapLibre はベクトルタイルで `tileZoom = floor(zoom)` を使うため、建物が現れる境界はマップズーム13.0になります（12.99以下は非表示）。ビューワの `kihonzu_*_line_building` の `minzoom: 13` と一致します。
- 最小ZLが13以上の縮尺（1/2,500 は ZL15〜16）では常に条件を満たすため、このフィルタは無影響です。`scripts/build.sh` は縮尺によらず同じフィルタを渡しています。
- 逆に**最大ZLが12以下の縮尺（1/25,000 は ZL2〜12）では建物が一切含まれなくなります**。1/25,000 を単体で使い建物が必要な場合は、`$zoom` の閾値を下げるかフィルタを外してください。
- タイルサイズの分布は [vt-optimizer-rs](https://github.com/unvt/vt-optimizer-rs) の `inspect` で確認できます。

### 1ファイルに結合する場合（任意）

配信ファイルを1つにまとめたい場合は `tile-join` で結合します。この場合は**ズーム範囲が重複しないよう tippecanoe の `-Z` を割り当て直してください**（1/25,000 → `-Z2 -z12`、1/10,000 → `-Z13 -z14`、1/2,500 → `-Z15 -z16`）。重複したまま結合すると、同じズームで複数縮尺のタイルが競合します。

```bash
tile-join \
  -o kihonzu.mbtiles \
  --force \
  --no-tile-size-limit \
  kihonzu_25000.mbtiles \
  kihonzu_10000.mbtiles \
  kihonzu_2500.mbtiles

pmtiles convert kihonzu.mbtiles kihonzu.pmtiles
```

## 利用上の注意

DMデータは測量法（昭和24年法律第188号）に基づく**公共測量成果**です。公共測量成果を複製または使用する場合は、原則として当該測量成果を得た**測量計画機関の承認**が必要です。

| 条文 | 内容 | 対象となる行為 |
|---|---|---|
| 測量法第43条 | 測量成果の複製 | 地図等を複製して測量に使用、刊行、または不特定多数に提供する場合 |
| 測量法第44条 | 測量成果の使用 | 測量成果を使用して測量を実施する場合 |

> 第29条・第30条は**基本測量**の測量成果（国土地理院が実施）に関する規定です。都市計画基本図は**公共測量**の成果にあたるため、第43条・第44条が適用されます。

上記「データ出典」の静岡市 都市計画基本図については、測量法第44条に基づく使用承認を得ています。

| 項目 | 内容 |
|---|---|
| 測量計画機関 | 静岡市 |
| 根拠 | 測量法第44条（測量成果の使用） |
| 承認番号 | 07静都都第2068号 |
| 承認日 | 令和8年1月20日 |
| **使用期間** | **承認の日より1年間（2027年1月19日まで）** |
| 使用目的 | 都市計画基本図を用いてベクトルタイルデータを作成し、クラウド環境を用いて地図タイルとして配信することにより、可視化手法および利活用可能性を検証・調査するため |

承認条件により、調製品には以下の文言を明記する必要があります（文言は承認書で特定されているため変更しないこと）。

> この地図は静岡市長の承認を得て、同市所管の2,500分の1及び10,000分の1静岡市地形図を使用して調製したものである。（承認番号07静都都第2068号）

あわせて、調製品を配信するWebサイトが静岡市の公式サイトであると誤認されないよう、個人が作成・配信するものである旨を明示する必要があります。

> **⚠️ 使用期間は2027年1月19日までです。** 期限を過ぎて継続利用する場合は、静岡市への再申請が必要です。

> **この承認は申請者に対して個別に与えられたものであり、本リポジトリの利用者に自動的に及ぶものではありません。** 同じデータを利用する場合は、別途、静岡市への承認申請が必要です。

> **承認されているのは第44条の「使用」であり、第43条の「複製」ではありません。** また使用目的は「地図タイルとして配信すること」に限定されています。変換済みデータそのものを配布する場合は、目的の追加を含めて別途申請が必要です。

他自治体のDMデータを変換して利用する場合は、当該自治体が定める複製・使用の手続きおよび利用条件に従ってください。
